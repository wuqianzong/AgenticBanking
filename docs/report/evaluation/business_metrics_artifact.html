Why redesign the v3.5 framework

v3.5 picked the right five things to instrument — containment, first-contact resolution, intent accuracy, groundedness, latency. Two things need fixing before that skeleton can carry a business argument.

1. Several of its cited data sources don't exist

It points at langgraph_state.db as a queryable SQLite checkpointer — the real one, MemorySaver(), is in-memory and wiped on every restart. It cites guardrail_violation.log — the real log is backend/logs/system.jsonl. The actual telemetry turns out to be richer than what v3.5 assumed; it just needs the citations corrected (see Data sources, below).

2. It leads with technical metrics, not business ones

F1 scores and time-to-first-token prove a system is well-engineered to an examiner. They don't prove to a COO that a rollout pays for itself. This framework puts cost, labour, and service quality at the top, and demotes the technical metrics to what they actually are: diagnostics that explain why the business numbers move.

Each metric below has a real measured baseline, and a placeholder for the one input only the bank itself can supply: real agent unit costs.

B1Automated Containment — the cost-and-labour headline

What it answers: of everything customers currently need a human for, how much can the bot take off the queue?

Why not v3.5's definition

v3.5 counts containment as failed only when a customer accepts an escalation offer. That signal is real, but it almost never fires in either completed study — soft_escalation_available was true in 0/3,552 BANKING77 turns and 6/1,964 multi-turn turns. Taken literally, that would report ~100% containment and tell operations nothing. This framework uses the three-tier split a call-centre already thinks in instead.

Cost translation — the formula is complete; it only needs the bank's real unit costs to become a dollar figure rather than an illustration:

Monthly Savings = (Fully-Contained Volume) × (Avg. Agent Handle Time) × (Fully-Loaded Agent Cost / min) − (Bot Operating Cost) Bot Operating Cost = (Total LLM calls) × (Per-call API cost) + (Infra)

Every llm.request is already timestamped and counted in both studies — this is a real, computable number the moment a per-call price is supplied, not a guess.

Honest caveat

Because soft_escalation_available almost never fires, the "needs a human" figures above mean the bot declined or asked for clarification, not a live hand-off was triggered and accepted — a genuinely different signal that needs an adaptive test harness (one that can react to the bot's own hand-off offer) to measure properly.

B1bDecomposing containment: Bot Reliability × KB Coverage

The problem this fixes: once the bot-failure defects below are fixed, remaining handoff volume will be almost entirely content gaps. One blended containment number then measures knowledge-base completeness, not bot reliability — different things, different owners, different timelines (content coverage rises purely from authoring FAQs, no code change needed).

The fix — the same split real contact centres already use for human agents (did the agent have the right knowledge-base article, vs. did the agent use it correctly), applied to the bot:

A retracted first attempt

A first pass tried to classify bot-vs-content failure automatically, flagging any unresolved case whose shown evidence contained a negation ("does not…", "cannot…"). Spot-checking 15 flags found it was matching negations from unrelated parts of the same document — discarded rather than reported. The number used instead is the manually-verified rate from the 88-case semantic sample (KNOWN_ISSUES_TRACKER.md BUG-016): 14.8% (95% CI 7.7%–21.8%) of shown-but-rejected tasks were confirmed genuine bot failures by direct human comparison.

A second label error, found and corrected 2026-09-13

A full open-bug review before finalizing this evaluation (per explicit instruction: check whether anything needs fixing or offsetting first) found that 22 of BUG-015's 24 confirmed cases (a generic failure fallback overwriting an already-resolved turn's text) still carried a task_results status of SUFFICIENT/RELEVANT — every automated metric here was silently counting a total customer-facing failure as a success. No code was fixed; the 26 affected tasks are now tracked as their own confirmed bot-failure category, separate from BUG-016's projected rate, since this one needed no projection — it's exactly known.

A discrepancy, reconciled — not just flagged

An earlier pass counted 973 unresolved tasks; a fresh full-corpus count found 1,036. The gap is real and now fully explained: 63 cases are declined or asked for clarification at the dispatcher stage, before any RAG task is ever created, so they never appear in task_results at all — the earlier count silently excluded them rather than double-counting or erroring.

Fixing BUG-016 resolves mostly this one category; it has no effect on the other nine.

Business implication: a topic recognized as one of the ten content-gap categories cannot be fixed by retrying generation — no prompt improvement conjures a fact that was never authored. Route those straight to a live-data source or a "let me get you that" hand-off with a content-authoring ticket, rather than spending latency and LLM spend on an attempt certain to fail. Retry budget belongs on the ~15% bot-failure share instead, where an engineering fix genuinely moves the number.

Grounding B1b in established standards, not an ad hoc split

Two independent, pre-existing precedents formalize exactly this decomposition — which also means the industry's own literature already warns why a single blended containment number is unsafe to compare across bots or vendors.

RAGAS (the same RAG-evaluation framework v3.5 itself cited for Metric 4) formally splits every evaluation into two independent halves, one per side of our split:

RAGAS metricWhat it measuresMaps to
Context Recall / Context PrecisionDoes the retrieved content contain what's needed, and is it relevantKB Coverage
Faithfulness / Answer RelevanceGiven what was retrieved, did the model use it correctly and stay groundedBot Reliability

This is the field's standard evaluation shape for any RAG system, not something invented for this project.

SQM Group's Source-of-Error framework, the standard root-cause methodology contact centres have used for decades to judge First Call Resolution failures, splits blame three ways: Customer 13%, Agent 38%, Organization 49% — where "Organization" specifically means policies, systems, and knowledge gaps, deliberately kept separate from agent skill so a human agent is never penalized for a knowledge-base gap outside their control. Our own split (85% content-gap / 15% bot-attributed) skews even further toward "organization" than that decades-old human baseline.

The caveat this grounding surfaces

The chatbot industry's own literature acknowledges the blended metric is manipulable — "gaps in the knowledge base are the most common cause of low containment" and best practice is to "track [KB coverage] as a separate metric from containment rate," while "standard containment metrics can actively mislead teams... you are manufacturing fake wins" if containment and true resolution diverge (Botpress). In practice this guidance is inconsistently followed — most published vendor containment numbers are blended, with no way to know from outside how much reflects content investment versus orchestration quality. Bot Reliability is the one claim here that can't be inflated just by adding more FAQ content — already normalized against whatever the KB contains — making it the correct number to lead with in any external or competitive claim about engineering quality.

Caveats that matter more than the raw comparison

(1) None of these external numbers are known to be decomposed the way B1b decomposes ours — read the comparison as illustrative positioning, not a rigorous match. (2) Escalation itself is barely exercised in either test corpus (0%/0.3% of turns) — our "handoff rate" means the bot declined or asked for clarification, not that a live hand-off was triggered and accepted. 86% of consumers want the option to reach a human, and 40% abandon entirely when they can't (2025 Salesforce study) — whether our escalation path is discoverable and trusted by real customers remains untested. (3) BANKING77 is a harder-than-real-life test by design (40 balanced queries across all 77 categories) — real production traffic, typically skewed toward common questions, would likely score higher, so 67.6–69.5% is best read as a floor.

The differentiated claim worth leading with: most cited industry figures are a single blended number with no visibility into what drives it. We can say something most competitors publishing a containment rate cannot: our containment already exceeds the mature-RAG average, and we can show exactly what moves it from here — content authoring for ~85% of the remaining gap, three named, already-diagnosed bug fixes for the rest.

B2Full-Session Resolution Rate — replaces FCR

What it answers: can the bot carry a customer through an entire multi-step need — not just one FAQ — in a single sitting?

The multi-turn study is direct evidence it can do something more valuable than answer one question: hold a customer through several linked asks (check balance, transfer, re-check balance, close out) inside one uninterrupted session, at 69.5% full resolution across all 249 sampled conversations, averaging 7.9 turns each. That's the stronger business claim — closer to "replaces a teller interaction" than "answers one FAQ."

Full-Session Resolution (%) = (Conversations where every turn resolved / Total conversations) × 100

Both baselines — 67.1% single-turn, 69.5% full multi-turn session — sit below a reasonable 80% target. A real, quantified gap; the next section explains most of where it comes from.

B3Customer Effort & Time-to-Resolution

Every second here is a direct tax on B1's savings.

Fairness, reframed

Neither study varies customer demographics, and the bot's design is not customer-specific — every request is evaluated fresh with no persisted profile shaping the outcome. So the applicable fairness test, per explicit direction, is not demographic variation but consistency: does the same underlying intent, in different customer wording, produce the same outcome? 24 of 77 BANKING77 categories fall below 60% concentration — the worst, declined_card_payment (35.0%), shows concrete evidence: "Why was my Payment declined" resolves, but "Please explain why my card was declined?" does not, for functionally the same question. Tracked as BUG-023.

Confirmed at scale with a second, embedding-based test: every subquery embedded with the production pipeline's own retrieval model and checked pairwise — even in the closest similarity band, only 60.9% of near-duplicate questions share an evidence basis. A more severe sibling result fell out of the same pass: isolating byte-identical repeated questions — the same sentence, no wording variation at all — finds a 35.2% split-outcome rate. No ambiguity argument can excuse that one; tracked separately as BUG-025.

Architectural mitigation shipped and live-validated. A cross-session answer cache now surfaces a historically-confirmed FAQ as an extra sufficiency-audit candidate for close-enough repeats. A live re-test through the real system found: re-running "I want to delete my account" 6 times gave 6/6 identical outcomes — up from 9/12 (75%) historically — even though live retrieval failed to find the right FAQ organically in all 6 fresh attempts; the cache alone carried every resolution. A parallel test on "Why was my payment declined?" reproduced the other half live: the identical cache-suggested candidate was present in all 4 runs, and the auditor still approved it twice and rejected it twice. This draws the exact line between what architecture can and can't fix: retrieval-pool consistency is solved; auditor-judgment consistency on identical evidence is a separate, model-behavior problem. Model-tuning fixes for it (self-consistency voting, a model-tier swap, rubric tightening) were considered and explicitly scoped out of this project by the user — "model tunning is out of scope, so what we can do is surface the same parent and keep the cache update" — so it stands as an accepted permanent limitation, not an open task (docs/FAIRNESS_ANSWER_CACHE_DESIGN.md S6a/S10).

Tier 3 · zero-toleranceTrust & Safety Guardrails

Banking is regulated and trust-sensitive: one bad incident here costs more than a percentage point moved on Tier 1 is worth. Tracked as absolute incident counts trending to zero, not a rate to maximize.

A different statistic than everywhere else in this document, deliberately

Every other confidence interval here (Bot Reliability, KB Coverage, Tool-Selection Accuracy) is two-sided — "what's our best estimate." Compliance is a one-sided question — what's the worst this could plausibly be — so these rows use a 95% one-sided upper confidence bound, via the exact binomial (Clopper-Pearson) method rather than a normal approximation (these are small counts of rare events, where a normal approximation is unreliable). This is the same method real financial and quality audits use ("attribute sampling"), and it turns "not observed" from an unquantified reassurance into an actual number: even zero observed incidents get a real bound.

Seven concrete next stepsWhat's Not Yet Measurable

1. Real unit costs (partially resolved). The API side of B1's cost formula is now real, computed from published pricing — what's still missing is the bank's own fully-loaded agent-minute cost, the other input to Monthly Savings.

AppendixStatistical Methodology

Every number in this framework falls into one of five measurement bases, each with a different level of confidence attached. Conflating them — reporting a sample-projected estimate with the same certainty as a full-corpus count — is the single easiest way to overstate precision.

BasisWhat it meansWhich metrics use it
Full-corpus, deterministicPulled directly from every case's own system-generated verdict — nothing sampled, nothing judged by a humanOverall Resolution, Containment/Handoff Rate, Turn-level resolution rate, Outbound audit pass rate
Full-corpus, automated proxyComputed across every case via an automated heuristic rather than a system-native verdict or human judgmentThe 950/23 retrieval-miss split; the 15/48 dispatcher-level split
Sample-based, manually verified, then projectedA human read a statistically-sized sample case-by-case; the resulting rate is applied to the full population, carrying that sample's confidence interval forwardThe 14.8% bot-failure rate underlying Bot Reliability/KB Coverage; the Service-Quality Index; Tool-Selection Accuracy (94.7%, n=94)
Full-corpus, deterministic proxy (no sampling)A per-category score computed from every case's own already-known outcome classification, with no new sampling beyond spot-checking the result for face validityThe Fairness outcome-concentration score (72.6% mean, 24/77 categories <60%)
Compliance/attribute sampling, one-sided upper boundA violation count against a known sample or corpus size, converted to "what's the worst this could plausibly be" via a 95% one-sided exact-binomial bound — never a two-sided normal-approximation CIEvery Tier 3 row with a real x/n behind it (13/619, 2/70, 6/3,080, 0/455)

Sample sizes were chosen deliberately, using the standard finite-population-corrected proportion formula for a 95% confidence interval:

n = n₀ / (1 + (n₀ − 1) / N), where n₀ = z² · p(1−p) / margin²

with z=1.96, p=0.5 (most conservative absent prior information). This produced n=385 (±5% margin) against N=3,080 for the BANKING77 semantic review, n=88 (±10%) against N=950 for the bot-failure sample, n=70 (±10%) against N=249 for the multi-turn semantic review, and n=94 (±10%) against N=3,275 for the Tool-Selection Accuracy sample — each sized to the population it was actually drawn from, not reused across different-sized populations.

Propagating sample uncertainty. Bot Reliability and KB Coverage each use the 14.8% (95% CI 7.7–21.8%) sample rate as an input. The correct way to report the result is to run the formula at both ends of that input's interval, not just its point estimate — reporting a bare percentage with no interval would silently claim a precision the underlying sample doesn't support.

Two reconciliations, not just caveats. An earlier draft reported an unresolved-task count (973) that didn't match a later, more complete count (1,036) — tracked down to 63 real cases a narrower script definition had silently excluded (dispatcher-level declines/clarifications that never reach task_results), not a data error. Separately, a full bug-tracker review before finalizing this evaluation found that 22 of BUG-015's 24 confirmed cases carried a task_results status of SUFFICIENT/RELEVANT despite the customer receiving a total-failure generic message — inflating every automated metric here by 26 tasks' worth until corrected. Neither bug was fixed; both were relabeled for accurate reporting instead. The corrected, five-category breakdown in B1b and the restated figures throughout this document are the result.
